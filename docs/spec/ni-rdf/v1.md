# ni-rdf 1: Named Information Identifiers for RDF Resources

- **Version:** 1 (procedure tag `ni-rdf/1`)
- **Status:** Draft. The version is frozen when the first release of kognio-rdf
  that mints `ni-rdf/1` identifiers is tagged: any later change is a new version
  with a new procedure tag, never an edit of this one.
- **License:** This specification and its test vectors are licensed under the
  [Creative Commons Attribution 4.0 International License](LICENSE)
  (CC BY 4.0). Implementations may be licensed in any way.
- **Test vectors:** [`vectors/v1.json`](vectors/v1.json)

## 1. Introduction

This specification defines how to derive a content-addressed identifier for one
RDF resource from the triples that describe it. The identifier is an RFC 6920
named information (`ni:`) URI:

```
ni:///sha3-256;<digest>
```

Two independent implementations that follow this specification derive the same
identifier for the same content, byte for byte. The identifier does not depend
on blank node labels, on the order of the triples, or on the IRI under which
the resource was described before it had an identifier. It does depend on every
other term of the description, except on the case of language tags.

The resource is named by a *base IRI* chosen by the caller. The *base IRI* and its
fragment IRIs (`<base#part>`) go into the *hashed input* as placeholders, not as
strings. A resource can therefore be described under a provisional IRI, given its
identifier, and then renamed to it; deriving the identifier again from the
renamed description yields the same identifier, which lets any reader verify
it.

RFC 6920 leaves the hash input to other specifications (RFC 6920, §2). This
specification defines it: a length-prefixed S-expression over the triples, with
blank nodes labelled by RDF Dataset Canonicalization (RDFC-1.0), opened by a
procedure tag that separates this procedure from every other.

### 1.1 Conformance

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this
document are to be interpreted as described in BCP 14 (RFC 2119, RFC 8174) when,
and only when, they appear in all capitals, as shown here.

An implementation conforms to this specification if, for every input, it either
returns exactly the identifier defined in §4 or fails with the failure defined
in §5 (or fails for lack of memory or similar operational resources, which no
specification can exclude), and if it reproduces every test vector in [`vectors/v1.json`](vectors/v1.json).
Sections marked *non-normative* do not contribute to conformance.

### 1.2 Terminology

- **Triple, IRI, blank node, literal, lexical form, datatype IRI, language
  tag:** as defined in RDF 1.1 Concepts and Abstract Syntax.
- **Graph:** a set of RDF 1.1 triples. A graph holds no duplicate triples.
- **String:** a sequence of Unicode code points. Strings are compared code point
  by code point, without any Unicode normalization.
- **UTF-8(x):** the UTF-8 encoding (RFC 3629) of the string `x`.
- **Base of an IRI:** the part of its string before the first `#`, or the whole
  string if it contains no `#`.
- **Fragment of an IRI:** the part of its string after the first `#`, which may
  be empty and may itself contain `#`. An IRI without `#` has no fragment.
- **Fragment IRI of an IRI `x`:** an IRI that has a fragment and whose base is
  `x`. `http://example.org/a#p1` and `http://example.org/a#` are fragment IRIs
  of `http://example.org/a`.
- **Base IRI:** the IRI that names the resource, an input of the procedure (§2).
- **Input graph:** the graph describing the resource, the other input of the
  procedure (§2).
- **Reserved IRI:** the string
  `urn:uuid:171650ec-eda4-47fd-9053-6a34696171c1`. It is a fixed UUID URN
  (RFC 9562) used internally by this procedure and never appears in an
  identifier.
- **Mapped graph:** the *input graph* after its language tags are lower-cased
  (§4.1) and the *base IRI* is replaced by the *reserved IRI* (§4.2).
- **Hashed input:** the byte sequence that is hashed into the digest (§4.5).

### 1.3 Overview (non-normative)

The procedure takes a *base IRI*, say `http://example.org/a`, and an *input graph*
that describes the resource it names:

```
<http://example.org/a> <http://purl.org/dc/terms/title> "Hello"@EN .
<http://example.org/a> <http://example.org/vocab#part> <http://example.org/a#p1> .
```

The description may use the *base IRI*, its fragment IRIs such as
`http://example.org/a#p1`, and blank nodes that hang off either. In plain
language, the procedure then:

1. **checks** that the *input graph* describes this one resource and nothing else:
   every IRI subject is the *base IRI* or one of its fragment IRIs, and every
   triple about a blank node can be reached from one of them (§3). Otherwise it
   fails with a code that says what is wrong (§5);
2. **lower-cases** the language tags, so `"Hello"@EN` and `"Hello"@en` are the
   same input (§4.1);
3. **takes the *base IRI* out**, by replacing it with a fixed *reserved IRI*, and
   its fragment IRIs with fragment IRIs of the *reserved IRI* (§4.2). From here on
   nothing depends on the string `http://example.org/a`;
4. **checks the cost** of labelling the blank nodes, and fails if it would be
   too high (§4.3);
5. **labels the blank nodes** canonically with RDFC-1.0, so the labels no longer
   depend on how the input happened to name them (§4.4);
6. **writes every triple** as a length-prefixed S-expression, in which the
   *reserved IRI* appears as the placeholder `S` and its fragment IRIs as `F`
   with their fragment, **sorts** these encodings by their bytes and wraps them
   in a list opened by the procedure tag `ni-rdf/1`. The result is the hashed
   input (§4.5, worked through for this example in §4.6);
7. **hashes** the *hashed input* with SHA3-256 (§4.7) and writes the digest into
   an `ni:` URI (§4.8).

For the example the identifier is
`ni:///sha3-256;J6D0-ZwcNChPBElhhwMFoqI9KBMoX3SauEhGFY3Y3SQ`. The resource can
now be renamed to it, fragment IRIs included:

```
<ni:///sha3-256;J6D0-ZwcNChPBElhhwMFoqI9KBMoX3SauEhGFY3Y3SQ> <http://purl.org/dc/terms/title> "Hello"@EN .
<ni:///sha3-256;J6D0-ZwcNChPBElhhwMFoqI9KBMoX3SauEhGFY3Y3SQ> <http://example.org/vocab#part> <ni:///sha3-256;J6D0-ZwcNChPBElhhwMFoqI9KBMoX3SauEhGFY3Y3SQ#p1> .
```

Running the procedure on this description, with the identifier as *base IRI*,
yields the same identifier again: step 3 replaces the identifier just as it
replaced `http://example.org/a`, so the *hashed input* is the same (§6).

## 2. Input and output

The input is a pair of a *base IRI* and an *input graph*:

- The **base IRI** is an absolute IRI string naming the resource.
- The **input graph** is a graph of RDF 1.1 triples describing that resource.

The output is either an identifier of the form `ni:///sha3-256;<digest>` (§4.8)
or a failure with one of the failure codes of §5.

The *input graph* MUST be valid RDF 1.1: in particular every IRI in it is an
absolute IRI. This specification defines no result for input that is not valid
RDF 1.1, with one exception that implementations can check cheaply and
uniformly: an IRI, the *base IRI* included, that begins with `_:` is no absolute
IRI, and is rejected (§3, condition 4).

Only the terms of RDF 1.1 are admitted. An input that holds an RDF 1.2 term —
a triple term, or a literal with a base direction — is rejected with
`UNSUPPORTED_TERM`. An implementation that cannot represent such terms at all
conforms by never accepting them.

## 3. Preconditions

An implementation MUST check the following conditions, and MUST fail with the
given code if one does not hold. If several conditions fail, the code of the
first failing condition in this list is reported.

1. The *base IRI* contains no `#`. Otherwise: `INVALID_BASE`.
2. The *base IRI* is not the *reserved IRI*. Otherwise: `RESERVED_IRI`.
3. The *input graph* holds at least one triple. Otherwise: `EMPTY_GRAPH`.
4. The *input graph* holds only RDF 1.1 terms, and neither the *base IRI* nor any IRI
   in the *input graph*, in any position and including datatype IRIs, begins with
   `_:`. Otherwise: `UNSUPPORTED_TERM`.
5. No IRI in the *input graph*, in any position and including datatype IRIs, has
   the *reserved IRI* as its base. Otherwise: `RESERVED_IRI`.
6. Every IRI that is the subject of a triple in the *input graph* has the *base IRI*
   as its base, that is, it is the *base IRI* itself or a fragment IRI of it. The
   comparison is an exact string comparison without URI normalization.
   Otherwise: `FOREIGN_SUBJECT`.
7. At least one triple in the *input graph* has an IRI subject. Otherwise:
   `NO_ROOT`.
8. Every triple in the *input graph* is *reachable* (below). Otherwise:
   `UNREACHABLE`.

**Reachability.** The set of reachable triples is the smallest set that contains
every triple of the *input graph* whose subject is an IRI, and every triple of the
*input graph* whose subject is a blank node that is the object of a reachable
triple. Reachability follows triples from subject to object only: a blank node
whose triples merely point at the resource, as in `_:x <p> <http://example.org/a>`
for the *base IRI* `http://example.org/a`, is not reachable.

*Note (non-normative):* condition 8 rejects rather than ignores unreachable
triples, because an identifier that ignores part of its input would let two
different graphs share one identifier.

## 4. Procedure

### 4.1 Language tags

Replace every language tag in the *input graph* by its lower-case form: every
character in the range `A`–`Z` is replaced by the corresponding character in
`a`–`z`, and all other characters are left unchanged. RDF 1.1 gives language
tags a lower-case value space and allows converting their lexical form to lower
case; this step makes `"x"@EN` and `"x"@en` the same input. It
MUST be applied before §4.3, because the blank node labels of §4.4 depend on it.

No other normalization is applied. In particular, lexical forms are not mapped
to canonical lexical forms: `"01"^^xsd:integer` and `"1"^^xsd:integer` are
different literals and yield different identifiers. A literal without a language
tag whose datatype IRI is not given has the datatype IRI
`http://www.w3.org/2001/XMLSchema#string`, as in RDF 1.1. A literal with a
language tag has the datatype IRI
`http://www.w3.org/1999/02/22-rdf-syntax-ns#langString`.

### 4.2 Mapping the base out

Produce the *mapped graph* by replacing, in every triple, every IRI `i` in every
position — subject, predicate, object, and the datatype IRI of a literal — as
follows:

- if `i` equals the *base IRI*: by the *reserved IRI*;
- else if the base of `i` equals the *base IRI* (so `i` has a fragment `f`,
  possibly empty): by the *reserved IRI* followed by `#` and `f`;
- otherwise: unchanged.

Precondition 5 guarantees that no IRI of the *input graph* maps to an IRI of the
form produced here, so the mapping is injective. The *mapped graph* is a set of
triples, like the *input graph*. Triples that become equal through §4.1 are one
triple of the *mapped graph*: two triples that differ only in `"x"@EN` and
`"x"@en` together contribute one triple, not two.

*Note (non-normative):* the mapping happens before canonicalization because
RDFC-1.0 orders blank nodes by hashes that include their neighbouring IRIs. If
the *base IRI* were still present, the blank node labels, and through them the
identifier, would depend on it.

### 4.3 Resource limit

An implementation MUST evaluate the following criterion on the *mapped graph*
before running RDFC-1.0 (§4.4), and MUST fail with `RESOURCE_LIMIT` if it is
exceeded. All arithmetic is exact integer arithmetic; an implementation MAY stop
as soon as it knows that the limit is exceeded.

1. For every blank node `n` in the *mapped graph*, compute its **first-degree
   hash** `h(n)` with the *Hash First Degree Quads* algorithm of RDFC-1.0 (§4.6
   of RDFC-1.0), treating the *mapped graph* as a dataset whose triples all lie in
   the default graph, with SHA-256 as the hash algorithm. A triple whose subject
   and object are both `n` is among the quads of `n` once per position, that is
   twice, as in §4.4.
2. A blank node `n` is **ambiguous** if another blank node `m` exists with
   `h(m) = h(n)`.
3. For an ambiguous blank node `n`, its **related ambiguous nodes** are the
   pairs (`k`, `m`) such that `m` is an ambiguous blank node, `m` ≠ `n`, and
   either
   - the *mapped graph* holds a triple with subject `n`, predicate `p` and object
     `m`, and `k` = (`out`, `p`, `h(m)`); or
   - the *mapped graph* holds a triple with subject `m`, predicate `p` and object
     `n`, and `k` = (`in`, `p`, `h(m)`).

   Group the related ambiguous nodes of `n` by `k`, and count the distinct blank
   nodes `m` in each group. The **orders** of `n` is the product, over its
   groups, of the factorial of the size of the group; it is 1 if `n` has no
   group.
4. Two ambiguous blank nodes are **connected** if some triple of the *mapped graph*
   has one of them as subject and the other as object. Let `C` range over the
   connected components of the ambiguous blank nodes under this relation. For a
   component `C`, let
   - `|C|` be the number of its blank nodes;
   - `W_C` be the product of the orders of the blank nodes of `C`;
   - `T_C` be the number of triples of the *mapped graph* whose subject or object
     is a blank node of `C`.
5. The **cost bound** is `E` = the sum over all components `C` of
   `W_C · |C| · (|C|² + T_C)`. The limit is exceeded if `E` is greater than
   **10 000 000**.

An implementation MUST NOT impose any other limit that rejects an input this
specification accepts, other than failing for lack of memory or similar
operational resources. In particular, it MUST NOT reject an input because
RDFC-1.0 runs longer than a time limit or a permutation count it sets itself.

*Note (non-normative):* RDFC-1.0 runs in factorial time on blank nodes it cannot
tell apart by their own triples and that have several mutually indistinguishable
neighbours: it tries every order of those neighbours, recursively. `W_C` counts
the orders of one component, and `|C| · (|C|² + T_C)` stands for the work on each.
Graphs without ambiguous structure — RDF lists, nested anonymous structures
written with `[ … ]` in Turtle, repeated identical anonymous nodes — cost next
to nothing however large they are. Two blank nodes with 7 identical blank-node
children each (`E` = 5 806 080) are accepted, with 8 children each rejected; a
directed cycle of 200 indistinguishable blank nodes (`E` = 8 080 000) is
accepted, one of 250 rejected.

The bound depends only on the graph, so every conforming implementation accepts
and rejects the same graphs, whatever its speed. It is argued and measured, not
proved: RDFC-1.0 refines the groups used here, and along one choice of orders
visits each blank node at most once per path; that is the reason to expect `E` to
track its work. Measured with titanium-rdfc on a battery of 37 graph shapes,
everything accepted took at most 434 ms and everything rejected that RDFC-1.0
could not finish within a second was above the limit. The bound is deliberately
conservative: it also rejects graphs that RDFC-1.0 handles quickly, for example
complete graphs of 4 to 6 blank nodes linked by one predicate, a cycle of 8 blank
nodes linked in both directions, and nested twin structures such as 2 × 2 × 6
identical children.

### 4.4 Blank node labels

Canonicalize the *mapped graph* with RDFC-1.0, treating all its triples as lying in
the default graph, with SHA-256 as the hash algorithm. This yields the *canonical
issued identifier* of every blank node: `c14n0`, `c14n1`, … . In §4.5 a blank
node is written as its canonical issued identifier, without the `_:` prefix.

The *blank node to quads map* of RDFC-1.0 refers to a triple from the entry of a
blank node once for every position in which that blank node occurs. A triple
whose subject and object are the same blank node, such as `_:x <p> _:x`, is
therefore among the quads of that blank node twice, and its line is hashed
twice by *Hash First Degree Quads* (§4.6 of RDFC-1.0).

*Note (non-normative):* RDFC-1.0 leaves this case open. Step 2.1 of its §4.4.3
reads: "For each blank node that is a component of Q, add a reference to Q from
the map entry for the blank node identifier *identifier* in the blank node to
quads map", which can be read as one reference per position or as one per
blank node. Some of its wording points to one reference per blank node: the
explanation that follows that step speaks of "the set of quads of which it is a
component", and its §3.1 defines the *mention set* of a node as "the set of all
quads … that mention" it, a term its §4.8.3 uses for the map entry. Other
wording points to a sequence that may repeat a quad: its §4.6.3 takes "the list
of quads" from the map entry and serializes each of them, without removing
duplicates. The two readings give a blank node with such a triple
different first-degree hashes, through them possibly different canonical issued
identifiers, and so possibly different identifiers. This specification fixes one
reference per position. Since all triples lie in the default graph, a triple holds a blank
node in at most two positions, so this is the only case in which the readings
differ; the later steps of RDFC-1.0 see the difference only through first-degree
hashes, because such a triple relates its blank node to no other blank node. The
vector `self-loop-beside-second-blank-node` covers it.

### 4.5 Serialization

**Length-prefixed string.** For a string `x`, `LS(x)` is the byte sequence
consisting of: the number of bytes of `UTF-8(x)` written in ASCII decimal digits
without leading zeros (`0` for the empty string), the ASCII character `:`, and
then `UTF-8(x)`. Example: `LS("abc")` = `3:abc`; `LS("é")` = `2:é` (two bytes).
There is no terminator.

**IRI.** An IRI `i` of the *mapped graph* is encoded as:

- `LS("S")` if `i` is the *reserved IRI*, which stands for the *base IRI*;
- `LS("F")` followed by `LS(f)` if `i` is the *reserved IRI* followed by `#` and
  `f`, which stands for a fragment IRI of the *base IRI* with the fragment `f`,
  possibly empty;
- `LS("I")` followed by `LS(i)` otherwise.

**Literal.** A literal with lexical form `v`, datatype IRI `d` and language tag
`t` (the empty string if it has none) is encoded as `LS("L")`, `LS(v)`, the
encoding of `d` as an IRI (above), and `LS(t)`, in this order. The datatype IRI
is always present (§4.1).

**Blank node.** A blank node with canonical issued identifier `c` is encoded as
`LS("B")` followed by `LS(c)`.

**Triple.** A triple is encoded as the ASCII character `(`, the encodings of its
subject, predicate and object in this order, and the ASCII character `)`.

**Document.** Encode every triple of the *mapped graph*. Sort the encodings in
ascending order, comparing them as sequences of unsigned bytes (a proper prefix
sorts first). The *hashed input* is the ASCII character `(`, then
`LS("ni-rdf/1")`, then the sorted triple encodings concatenated, then the ASCII
character `)`.

*Note (non-normative):* every term begins with its kind tag, and every
component is length-prefixed, so the encoding is injective: distinct triples
never share an encoding, no field can be mistaken for the next, and no IRI or
literal can spell the placeholders `S` and `F`. The procedure tag `ni-rdf/1`
separates this procedure from any later version: two versions cannot yield the
same *hashed input* for the same content.

### 4.6 Example (non-normative)

For the *base IRI* `http://example.org/a` and the *input graph*:

```
<http://example.org/a> <http://purl.org/dc/terms/title> "Hello"@EN .
<http://example.org/a> <http://example.org/vocab#part> <http://example.org/a#p1> .
```

The language tag is lower-cased (§4.1), the *base IRI* becomes the placeholder `S`
and `<http://example.org/a#p1>` the fragment `F` `p1` (§4.2, §4.5); no blank
nodes occur.

The *hashed input* is (shown on several lines; the bytes contain no line breaks):

```
(8:ni-rdf/1
(1:S1:I29:http://example.org/vocab#part1:F2:p1)
(1:S1:I30:http://purl.org/dc/terms/title1:L5:Hello1:I53:http://www.w3.org/1999/02/22-rdf-syntax-ns#langString2:en)
)
```

The triples sort by their bytes, so the length prefix `29` of the first
predicate puts its triple before the one whose predicate has `30` bytes,
whatever the IRIs themselves say.

The identifier of this example is the first vector in
[`vectors/v1.json`](vectors/v1.json).

### 4.7 Digest

The digest is SHA3-256 (FIPS 202) of the *hashed input*.

### 4.8 Identifier

The identifier is the string `ni:///sha3-256;` followed by the base64url
encoding (RFC 4648, §5) of the 32-byte digest, without padding (43 characters).

This is the **canonical form**. It has no authority and no query, and the
algorithm string is exactly `sha3-256` in lower case. Anything that writes the
identifier into RDF MUST use the canonical form. RFC 6920 treats
`ni://example.org/sha3-256;X` and `ni:///sha3-256;X?ct=text/plain` as the same
name as `ni:///sha3-256;X`, but RDF compares IRIs as strings; a consumer that
receives another spelling should normalize it to the canonical form before storing
or comparing it.

## 5. Failures

An implementation MUST NOT return an identifier for an input that fails a
condition of §3 or the limit of §4.3. It SHOULD report the failure code, so that
callers and test suites can tell the failures apart.

| Code | Meaning |
|---|---|
| `INVALID_BASE` | The *base IRI* contains `#`. |
| `RESERVED_IRI` | The *base IRI* is the *reserved IRI*, or an IRI of the *input graph* has the *reserved IRI* as its base. |
| `EMPTY_GRAPH` | The *input graph* holds no triple. |
| `UNSUPPORTED_TERM` | The *input graph* holds an RDF 1.2 term, or an IRI (the *base IRI* included) that begins with `_:`. |
| `FOREIGN_SUBJECT` | An IRI subject is neither the *base IRI* nor a fragment IRI of it. |
| `NO_ROOT` | No triple has an IRI subject. |
| `UNREACHABLE` | A triple is not reachable from an IRI subject. |
| `RESOURCE_LIMIT` | The cost bound of §4.3 exceeds 10 000 000. |

## 6. Using the identifier (non-normative)

**Renaming.** Once the identifier is known, the resource can be renamed: the
*base IRI* becomes the identifier and every fragment IRI of the *base IRI* with the
fragment `f` becomes the identifier followed by `#` and `f`, in every position
including datatype IRIs. Deriving the identifier of the renamed graph, with the
identifier as *base IRI*, yields the same identifier again. A reader holding the
description and the identifier can thereby verify that one belongs to the other.

**Fragment IRIs.** RFC 6920 defines no fragment, but RFC 3986 allows one on any
URI reference. The digest is base64url and contains no `#`, so the base of a
fragment IRI of the identifier is the identifier.

**Resolution.** This specification defines no resolution. RFC 6920 §4 maps names
to `/.well-known/ni/` URLs and expects that a retriever can check what it
receives against the name. A standard RFC 6920 client hashes the bytes it
fetched; it can verify a name of this specification only if what is served is
the *hashed input* itself, which is not an RDF serialization. An application
serving RDF under such a URL makes no promise that a plain byte check succeeds.

**Version.** The name does not show which procedure version produced it. A
verifier that cannot reproduce a digest cannot tell an unknown procedure version
from altered content. A verifier tries the versions it supports.

## 7. Security and privacy considerations (non-normative)

- **No authorship.** The digest binds content, not an author. Binding an author
  takes a signature.
- **Erasure.** Content addressing makes erased content provable: anyone holding
  a copy can show, after an erasure, that it is exactly the content a
  still-circulating identifier names.
- **Guessing.** A digest over small, predictable content can be confirmed by
  hashing candidates. The identifier is not a means of hiding content.
- **Denial of service.** §4.3 bounds the estimated canonicalization cost of
  accepted graphs. An implementation evaluates it before RDFC-1.0, so a poison
  graph is rejected before its cost is paid. The bound is an estimate (§4.3, note),
  not a proof of a time limit.

## 8. Changes in later versions (non-normative)

A later version gets a new procedure tag. Known reasons for one:

- **RDF 1.2.** RDFC-1.0 is defined over RDF 1.1 datasets. Once canonicalization
  of triple terms and of literals with a base direction is standardized, a
  later version can admit them.

## 9. Test vectors

[`vectors/v1.json`](vectors/v1.json) holds a JSON object with a member `vectors`,
an array of objects with these members:

| Member | Content |
|---|---|
| `id` | A unique, stable name of the vector. |
| `description` | What the vector exercises. |
| `base` | The *base IRI*. |
| `input` | The *input graph* as an N-Triples document (RDF 1.1, UTF-8). |
| `name` | The expected identifier, or absent if a failure is expected. |
| `hashed` | The expected *hashed input*, decoded from UTF-8 into a JSON string, or absent if a failure is expected. Characters such as TAB stand in it as themselves (JSON-escaped only as JSON requires), not in N-Triples escaping. |
| `failure` | The expected failure code of §5, or absent if an identifier is expected. |

Each vector expects either `name` and `hashed`, or `failure`. Where several
vectors describe the same content, they expect the same `name`. Vector input is
RDF 1.1 N-Triples, which can express neither RDF 1.2 terms nor an IRI that begins
with `_:`, so `UNSUPPORTED_TERM` has no vector.
